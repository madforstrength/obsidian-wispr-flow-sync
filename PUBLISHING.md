## 2. Initialise and commit

`main.js` is intentionally gitignored — it's a **build artifact** attached to every GitHub release, not source code. Seeing it absent from `git status` is correct, not a sign something is broken; do not `git add -f` it.

```bash
git init -b main
git add .
git status --short          # review before committing
git commit -m "Initial commit: Wispr Flow Sync plugin"
```

Success looks like: `git status --short` (before committing) shows source files, config, `PUBLISHING.md`, `README.md`, `LICENSE`, workflow files, etc. — but no `main.js`, no `node_modules/`, and no `src/wispr/wasmBinary.ts`. Those three are gitignored on purpose (the last one is generated by `npm run inline-wasm` and must never be committed either — see the CI note in step 5). After `git commit`, `git log --oneline` should show exactly one commit.

## 3. Create the GitHub repository and push

**Option A — using the `gh` CLI** (if installed and authenticated via `gh auth login`):

```bash
gh repo create obsidian-wispr-flow-sync --public --source=. --remote=origin --push
```

This creates the repo under your account, wires up `origin`, and pushes `main` in one step. Success looks like a printed repo URL such as `https://github.com/madforstrength/obsidian-wispr-flow-sync`.

**Option B — manual route** (create the repo in the GitHub web UI first, with no README/license/gitignore — this repo already has all three):

```bash
git remote add origin https://github.com/madforstrength/obsidian-wispr-flow-sync.git
git push -u origin main
```

Success looks like: refreshing the repo page on github.com shows your files, and `git status` locally reports the branch is up to date with `origin/main`.

## 4. Cut the release

Obsidian matches the GitHub release tag against `manifest.json`'s `"version"` field **literally, as a string** — not as a semantic version. `manifest.json` currently declares `"version": "0.1.0"`, so the tag must be exactly `0.1.0`.

**This is the single easiest step to get wrong.** The instinct from other ecosystems is to prefix tags with `v` (`v0.1.0`). Do not do that here — a `v`-prefixed tag will not match `manifest.json`, Obsidian will not resolve the release, and the plugin will silently fail to install or update for anyone using it. `.github/workflows/release.yml` (added in this same change) asserts tag-equals-manifest-version and will fail the workflow loudly rather than publish a broken release, but it's simpler to just get the tag right the first time.

```bash
git tag 0.1.0
git push origin 0.1.0
```

Pushing the tag triggers `.github/workflows/release.yml`, which: installs dependencies, runs `npm run inline-wasm` (required — see step 5's checkpoint note), typechecks, runs the test suite, builds `main.js` in production mode, asserts the tag equals `manifest.json`'s version, and then creates a GitHub release attaching `main.js` and `manifest.json` **as individual files**. Do not attach a zip archive — Obsidian and BRAT both expect these two files (plus optional `styles.css`, which this plugin does not have) to be individually downloadable release assets, not packaged together.

Success looks like: a new "Actions" run on GitHub goes green, and the repo's "Releases" page shows a release titled `0.1.0` with exactly two assets, `main.js` and `manifest.json`. If the Actions run fails at the "Tag must equal manifest version" step, the error message will tell you the tag and the manifest version it compared — delete the bad tag (`git tag -d 0.1.0 && git push origin :refs/tags/0.1.0`), fix whichever side is wrong, and re-tag.

## 5. Beta-test with BRAT before the store listing exists

Before submitting to the community plugin directory (which involves a review queue and takes time), get real usage on the release you just cut. Install the **Obsidian42-BRAT** plugin from Obsidian's Community Plugins browser, then in BRAT's settings choose "Add a beta plugin" and enter:

```
madforstrength/obsidian-wispr-flow-sync
```

BRAT installs directly from your GitHub release (the one from step 4) — no store listing required.

This matters more than usual for this plugin specifically: Wispr Flow's Notetaker feature — the thing that produces the meeting notes and transcripts this plugin reads — shipped only days before this plugin was written, and its on-disk database schema is undocumented by Wispr. Schema drift (Wispr changing the database layout in a future update) is therefore the most likely source of breakage, and real users on real Wispr Flow installs will surface that far faster than manual testing on one machine will. Treat early BRAT installs as your schema-drift early-warning system, not just a formality.

## 6. Submit to the community plugin directory

The current submission route is **community.obsidian.md**, not a pull request:

1. Go to community.obsidian.md and sign in with an Obsidian account.
2. Link your GitHub account so the directory can verify you own the repository.
3. Add the plugin from your repository.

The directory reads `manifest.json` directly from your repository's HEAD (the `main` branch), so make sure whatever is pushed there is what you want reviewed and listed.

After submission, automated and human review may leave feedback (for example, about the `fetch(` occurrences noted in the checklist below). Address feedback by pushing a fix to `main` and cutting a new release with an **incremented** version (update `version` in both `manifest.json` and `package.json`, add an entry to `versions.json`, then repeat step 4 with the new version number as the tag) — do not try to reuse or overwrite the `0.1.0` tag.

**If you find older guides that describe opening a pull request against `obsidianmd/obsidian-releases`:** that was the previous submission process and may still be referenced in blog posts, forum threads, or outdated documentation. It is no longer how new plugins are submitted — use the community.obsidian.md flow above instead.

## 7. Pre-submission checklist

Before submitting, confirm all of the following:

- [ ] `manifest.json`'s `id` is `wispr-flow-sync` and `name` is `Wispr Flow Sync` — neither contains the word "Obsidian" (not permitted in plugin names/ids).
- [ ] `manifest.json` has `"isDesktopOnly": true` and `"minAppVersion": "1.13.0"` — raised from 1.5.0 when the settings tab moved to the declarative `getSettingDefinitions()` API, which does not exist before 1.13.0.
- [ ] `manifest.json`'s `description` is under 250 characters, starts with a verb, ends with a period, and contains no emoji.
- [ ] `README.md` and `LICENSE` are both present at the repository root.
- [ ] The release tag equals `manifest.json`'s `version` exactly (currently `0.1.2`, no `v` prefix).
- [ ] The release has `main.js` and `manifest.json` attached as individual files, not zipped together.

## 8. What to expect on review

Reviewers (automated or human) commonly grep release bundles for network-access indicators. `main.js` contains two occurrences of the literal string `fetch(`. Both are dead code paths inside the bundled Emscripten WebAssembly loader that ships with the `wa-sqlite` dependency — the plugin always supplies the WASM binary inline via `wasmBinary`, so the loader's own `fetch`-based fallback paths are never reached. This is already documented in `README.md` under **Disclosures → "A note on `fetch` in `main.js`"**, including how it was verified (a spy on `globalThis.fetch` that throws on any call, exercised through a full sync, with zero calls observed). If a reviewer flags this, point them at that section rather than re-explaining it from scratch.
